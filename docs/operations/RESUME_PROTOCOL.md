# 세션 독립형 자율 개발 운영 규정 v1.2

## 목적과 권한
사용자 지시: 채팅 GPT가 안전하게 처리할 수 있는 개발을 최대한 선행한다. Codex 사용량과 중복 개발을 줄인다. 사용자는 반복해서 상세 WO를 지정할 필요가 없다.
"다음 작업", "작업 시작", "작업 재개", "계속 진행"은 저장소의 현재 상태를 확인하고 다음 안전한 작업 묶음을 직접 선택·수행하라는 승인이다. 설명만 출력하지 말고 가능한 범위에서 변경·검증·기록까지 수행한다.
이 권한은 사용자가 메시지를 보낸 현재 작업에 한정한다. 대화가 종료된 뒤 백그라운드 작업을 약속하지 않는다. 자동 릴리스, 유료 서비스, 시크릿 발급, 실제 사용자 기기 변경, 강제 푸시 및 데이터 파괴에는 적용하지 않는다.

## 1. 매 작업 턴 복원 (PRE-FLIGHT)
[루트 AGENTS.md](../../AGENTS.md)의 PRE-FLIGHT를 모든 작업 요청의 첫 행동으로 실행한다. 같은 대화의 후속 턴에도 생략하지 않는다. 이전 턴의 확인 결과를 재사용하지 않는다. 필수 문서 확인 및 증거 대조를 마치기 전에는 구현·수정·테스트 실행·커밋·작업 확정을 하지 않는다. 확인이 차단되면 안전한 읽기 전용 진단과 상태 정정만 수행한다.

1. 저장소 scarlel96-design/AURA-Ultra의 실제 main HEAD를 조회한다.
2. HEAD에 고정해 AGENTS.md, docs/STATUS.md, 이 문서, docs/operations/GPT_EXECUTION_PLAN.md, docs/operations/PROJECT_INVARIANTS.md를 읽는다.
3. [TASK_RECORD_PROTOCOL.md](TASK_RECORD_PROTOCOL.md), [VERIFICATION_PROTOCOL.md](VERIFICATION_PROTOCOL.md), [TASK_REPORT_TEMPLATE.md](TASK_REPORT_TEMPLATE.md)를 읽는다. 현재 작업 ID와 차단 ID를 찾는다. docs/operations/BLOCKERS.md, docs/operations/WORK_LOG.md의 관련 최근 기록, docs/ROADMAP.md와 관련 WO 명세·증거를 읽는다.
4. 활성 작업의 실제 소스, CI 설정, 최신 관련 실행 결과와 변경 이력을 확인한다. 현재 HEAD와 CI 검사 SHA를 구분한다.
5. 현재 환경의 도구, 파일 쓰기 권한, 네트워크, CI, 기기 접근 가능성을 확인한다.
6. 기존 기록과 실제 소스/증거가 불일치하면 상태를 정정한다. 기준 SHA, 확인 문서, 활성 작업, 차단점 및 PRE-FLIGHT 판정을 해당 작업 보고서에 기록한다. 과거 대화 기억이나 이전 에이전트의 완료 주장만 신뢰하지 않는다.

기록이 누락됐으면 확인 가능한 소스와 증거에서 상태를 복원한다. 확인 불가능한 사항은 UNKNOWN 또는 NOT RUN으로 기록한다. 사용자에게 이미 문서화된 정보를 다시 요청하지 않는다.

## 2. 다음 작업 선택
우선순위는 다음과 같다.
1. 보안·데이터 무결성·기존 핵심 기능 회귀.
2. 현재 빌드 또는 필수 검증 차단 문제.
3. 현재 GPT 작업 묶음의 미완료 산출물.
4. 의존 조건이 충족된 다음 GPT 작업 묶음.
5. 차단 문제와 무관한 독립 작업(테스트 가능한 순수 로직, 명세, 테스트 도구 등).

동일 우선순위에서는 선행 의존성, 재작업 위험, Codex 작업량 절감 효과, 검증 가능성 순으로 선택한다. "다음 작업"마다 작업 시작 전에 짧은 범위·근거·판정 기준을 제시한다. 새 번호를 만들기 전에 기존 미완료 항목을 확인한다.

WO는 제품 요구사항의 공식 작업 단위다. GPT-NN은 채팅 작업 묶음이며 WO를 대체하지 않는다. GPT 묶음 완료는 관련 WO의 공식 GO를 뜻하지 않는다. 선행 WO가 PARTIAL인 경우 독립적이고 되돌릴 수 있는 준비 작업만 진행한다. 그 준비 작업과 미충족 선행 조건을 명시한다. 승인된 설계의 필수 출시 게이트를 우회하지 않는다.
사용자의 "다음 작업"은 준비된 다음 WO 또는 독립 하위 작업의 착수 승인으로 인정한다. 매번 별도 승인을 요청하지 않는다. 한 요청 안에서 안전하게 완료할 수 있는 관련 하위 작업을 묶어 수행한다. 다음 요청에는 실제 체크포인트부터 재개한다.

## 3. 실행 및 증거
- 모든 작업에 TASK_RECORD_PROTOCOL 및 VERIFICATION_PROTOCOL의 G0~G7을 적용한다. 시작 전 보고서 초안을 작성한다. 작업 후 요구사항-구현-시험-증거 대조 및 별도 재검토를 수행한다.
- 변경 전 기준 SHA, 목표, 요구사항 ID, 관련 WO, 수정 파일, 제외 범위, 검증 명령과 위험을 기록한다. 상세 WO가 없으면 TEMPLATE에 따라 해당 작업의 실행 명세를 먼저 작성한다.
- 읽기 전용 조사, 스키마 확인, 작은 재현 시험을 먼저 수행한다. 오류를 실제 로그로 재현하거나 식별한다.
- 기존 통합 구조를 유지한다. 관련 없는 파일은 변경하지 않는다. 가능한 작은 커밋으로 분리한다.
- 모든 시험에 명령, 대상 SHA, 환경, 결과, 로그 링크를 기록한다. 필수 시험 실패를 숨기거나 SKIP으로 변경하지 않는다.
- CI가 실행 중이면 PENDING으로 기록한다. 새로운 요청에서 확인한다. 실제 성공 전 GO를 부여하지 않는다.
- 정적 검사, 빌드 성공, 런타임 검증, 실기기 품질 검증은 별개의 결과다.
- main 반영 전 현재 HEAD를 재확인한다. expected SHA와 fast-forward를 사용한다. 다른 작업자의 변경이 있으면 재검토한다. 승인되지 않은 강제 푸시를 하지 않는다.
- 중요 구현은 검증 브랜치/PR을 우선한다. 사용자가 승인한 현재의 초기 개발 방식에서는 저위험 문서·도구 수정의 main 반영도 가능하다. 실패한 검증을 성공으로 표시하지 않는다.

## 4. 작업 종료 시 필수 갱신
TASK_REPORT_TEMPLATE의 모든 적용 항목을 채운다. 문서 기반 재개 경로와 실제 반영 여부를 확인한다. 기록이 저장되지 않았으면 작업 완료를 선언하지 않는다.
docs/STATUS.md: 현재 단일 재개 체크포인트. 활성 GPT/WO, 단계, 다음 행동, 미완료 조건, 관련 코드 커밋, 최신 확인 CI 및 남은 시험을 갱신한다.
docs/operations/WORK_LOG.md: 새 항목을 시간순으로 추가한다. 과거 항목을 덮어쓰지 않는다.
docs/operations/BLOCKERS.md: 새 장애, 원인 가설, 증거, 해결 조건, 담당 환경을 갱신한다.
docs/evidence/WO-NN/ 또는 docs/evidence/GPT-NN/: 해당 작업의 실제 검증 보고서를 기록한다.
필요하면 docs/operations/HANDOFF.md, PROGRESS_MODEL.md에 근거를 추가한다. 아키텍처 변경은 ADR에 기록한다.

자기 참조 커밋 SHA는 만들 수 없다. 보고서에서 검증한 코드 SHA 또는 부모 SHA를 명시하고, 문서 커밋은 Git 이력에서 확인한다. 문서만 바꿔도 CI가 다시 실행될 수 있으므로 마지막 코드 검증 SHA와 최신 HEAD를 혼동하지 않는다.

## 5. 중단·인수인계
현재 작업을 완결할 수 없으면 완료한 산출물과 정확한 재개 행동을 저장한다. 차단 항목에 해결 조건을 기록한다. 안전한 독립 작업이 있으면 먼저 진행한다. 외부 기기·사용자 권한·실제 계정·서명키·비용·범위 변경이 반드시 필요하거나 안전한 대안이 없을 때만 사용자에게 요청한다.
단순히 채팅 모델의 처리 한계나 시간 제한 때문에 작업을 완료한 것으로 판정하지 않는다. Codex 인수는 남은 작업이 해당 환경을 요구할 때만 제안한다.
