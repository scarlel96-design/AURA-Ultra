# 작업별 심층 검증 및 품질 게이트 v1.1

이 규정은 모든 변경에 적용한다. [QUALITY_GATES](../QUALITY_GATES.md)의 제품 출시 기준을 완화하지 않는다. 문서 작업은 문서에 적용되는 시험을 수행한다. 제품 코드를 바꾸지 않았더라도 이미 알려진 제품 실패를 PASS로 바꾸지 않는다.

## G0 — 사전 검증
요구사항, 승인 범위, 선행 조건, 대상 버전, 기본 상태의 테스트 결과를 확인한다. 기존 실패와 이번 변경으로 발생한 실패를 구분한다.
변경 영향 범위를 조사한다. 호출자, 데이터 계약, 다른 WFF 프로필, 리소스, 빌드, 테스트, 권한, 저장소 및 문서를 포함한다. 위험도에 맞게 시험 범위를 정한다.

## G1 — 요구사항 충족 및 구현 검토
요구사항별 기대 결과와 실제 구현 파일을 연결한다. 해당 요구사항에 대한 시험과 증거를 연결한다.
원래 의도, 예외, 플랫폼 제약, 미구현 경로, API 지원 버전, 잘못된 기본값, 무의미한 placeholder를 검사한다.
정상 동작만 보지 않는다. 경계값, 비정상 입력, 데이터 누락, 권한 거부, 순서 역전, 중복 호출, 타임아웃, 연결 끊김 및 복구를 영향 범위에 따라 검사한다.
필요한 오류 처리와 데이터 유효기간을 확인한다. 기존 계약과의 호환성을 확인한다.

## G2 — 검증 도구 자체 검증
테스트 및 검사기가 실제 결함을 검출하는지 확인한다. 성공 경로와 의도적으로 잘못된 입력을 포함한다. 변경된 검증 도구에는 실패 탐지 회귀 시험을 추가한다.
단순 문자열 포함, 성공처럼 보이는 출력, 테스트 미발견, 묵시적 성공, 잘못된 종료 코드 처리, 비어 있는 입력 목록, 잘못된 대상 버전, 누락된 빌드 프로필 및 잘못된 fixture를 검사한다.
공식 WFF validator는 대상 XML과 버전의 명시적 성공 판정 및 종료 상태를 확인한다. 일반 헤더의 "Validation" 또는 "VALID" 포함 여부만으로 판정하지 않는다. 잘못된 XML·버전 입력에서 실패하는지 검증한다.
APK 검사기는 정확한 ZIP 항목, 병합 Manifest, 대상 APK를 확인한다. 실행 코드 검사를 우회하지 않는다. 실제 결함인지 검사 오탐인지 증거로 구분한다.
테스트를 삭제하거나 약화해 통과율을 높이지 않는다. 승인된 사유와 대체 검증 없이 assert, threshold, golden, 필수 CI 단계를 변경하지 않는다. 실패 종료 코드를 무시하지 않는다.

## G3 — 자동 시험 및 회귀
신규 기능의 단위·통합 시험과 기존 관련 회귀 시험을 실행한다. 공통 인터페이스, 빌드, 검증기 또는 생성기 변경에는 영향받는 모든 대상 프로필과 관련 CI를 실행한다.
실패한 시험을 수정한 뒤 해당 시험을 재실행한다. 이어 관련 회귀 시험을 다시 실행한다. 모든 변경은 최종 코드 SHA의 증거로 평가한다.
가능하면 clean build와 재현 가능한 자산 생성도 검증한다. 캐시나 이전 APK를 새 빌드 결과로 사용하지 않는다.
시험 개수와 PASS, FAIL, SKIP, NOT RUN, PENDING을 기록한다. 실행된 시험이 0개라면 PASS라고 표시하지 않는다. 필수 시험 미실행은 PARTIAL 또는 NO-GO로 판정한다.

## G4 — 기술 분야별 검사
| 분야 | 적용 검사 |
|---|---|
| WFF | 버전별 공식 스키마, 리소스 참조, 실제 APK, 병합 Manifest, 실행 코드 금지, AOD/메모리 |
| 그래픽 | 원형 안전 영역, 모든 해상도, 긴 문자열, 대비, 레이어·광원·정밀도, 승인된 시각 기준 |
| 모션 | 이벤트 트리거, 전환 순서, 연속성, 빠른 재진입, 반복·잔상, 모션 감소, 실제 영상 |
| 데이터/FSM | 값 범위, 단위, 시간대, TTL, 관측/예측 구분, 우선순위, 히스테리시스, 캐시·복구 |
| 건강/네트워크 | 권한·철회, 출처, 오류 응답, 백오프, 민감정보, API 키 노출, 공식 SDK |
| 성능 | 공식 메모리 한도와 목표, 발광 픽셀, 프레임 및 전력·발열의 실제 조건 비교 |
| 앱/동기화 | 수명주기, 버전, 연결 끊김/재연결, 데이터 일치, 설정 이전, 설치/업데이트 |
| 보안/공급망 | 최소 권한, 저장·로그, 무결성, 의존성·라이선스, 변경 영향 |
| 문서 | 요구사항 보존, 경로·ID·명령, 실제 코드 및 증거 일치, 재개 가능성 |

그래픽 콘셉트, 정적 프리뷰, 공식 스키마 및 에뮬레이터는 실기기 시각 승인이나 배터리 측정을 대신하지 않는다. 기기가 필요하면 해당 시험을 NOT RUN으로 유지한다.

## G5 — 구현 후 별도 검토
구현 단계와 분리된 검토 회차에서 실제 변경 diff와 정본 요구사항을 다시 읽는다. 구현자의 설명만으로 적합성을 판단하지 않는다.
누락, 잘못된 가정, 경계값 오류, 회귀, 보안 위험, 과도한 복잡성, 중복, 테스트 미검출, 문서 불일치를 찾는다.
다른 에이전트가 접근 가능하면 위험도가 높은 변경에 독립 리뷰를 요청할 수 있다. 같은 GPT가 재검토한 경우 자기 재검토라고 기록한다. 별도 모델 또는 사람의 독립 승인을 받았다고 주장하지 않는다.
문제마다 ID, 심각도, 위치, 재현 방법, 증거, 수정 또는 후속 조치, 재검증 결과를 기록한다. 발견된 필수 결함을 해결하지 못하면 해당 작업을 GO 처리하지 않는다.

## G6 — 증거 및 판정 감사
최종 변경 SHA, CI head SHA, 검사 대상 파일/프로필, 명령, 종료 상태, 로그의 실제 판정, APK/Artifact의 존재 및 검증 대상이 일치하는지 확인한다.
CI의 job conclusion만 보지 말고 관련 step 결과와 실패·경고 원문을 확인한다. 검증한 코드가 후속 커밋으로 바뀌면 영향받는 시험을 다시 실행한다.
요구사항 추적표의 모든 필수 행이 충족되었는지 확인한다. 미충족 사항은 BLOCKERS 및 STATUS에 남긴다.
문서의 GO와 실제 CI FAIL이 충돌하면 실제 증거를 우선한다. 문서 작업 GO와 기존 제품 NO-GO는 공존할 수 있다.
승인된 작업 단위의 종료 기준에 필요한 검증이 모두 충족될 때만 GO. 필수 검증이 불완전하면 PARTIAL. 필수 실패 또는 차단 위험이면 NO-GO. 실기기 미검증 기능을 정식 출시 기능으로 판정하지 않는다.

## G7 — 기록·재개 검증
[TASK_RECORD_PROTOCOL.md](TASK_RECORD_PROTOCOL.md)에 따라 보고서, STATUS, WORK_LOG, BLOCKERS, 관련 정본 명세를 갱신한다. 실제 저장소 반영을 확인한다.
후속 작업의 첫 명령과 예상 결과를 기록한다. 이 검사가 끝나야 작업 종료 보고를 제출한다.

## 결함 심각도
P0: 보안·데이터·빌드·필수 기능 또는 검증 신뢰성을 차단하는 결함. 관련 작업 즉시 우선.
P1: 주요 기능·호환성·시각 품질·성능의 중대 결함. 해당 작업 또는 출시 GO 차단.
P2: 제한된 영향의 결함. 요구사항 및 승인 조건에 따라 수정 또는 명시적 이관.
P3: 비차단 문서·유지보수 개선. 후속 큐에 기록.
심각도는 재현 증거와 영향에 근거한다. 새로운 실패를 낮은 심각도로 분류하여 숨기지 않는다.
